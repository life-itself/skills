# Changelog roll-up

Aggregates per-project changelog entries into a personal weekly draft, and handles the manual-promote step for anything flagged. This is a separate concern from writing an individual project's changelog entry — see [PUBLISHING.md](https://raw.githubusercontent.com/life-itself/changelog/main/PUBLISHING.md) in `life-itself/changelog` (fetch it if the process below is unclear or hasn't run in a while; that file is canonical, this is the working copy).

Run this **during** the weekly review (alongside or after the `planning` skill's week mode), not as its own separate session unless asked.

## Steps

1. **Find active workspaces.** Read both `projects/*.md` and `initiatives/*.md`, filtered to `status:` that isn't `done`/archived. Exclude records under `parent: [[household-operations]]`: they are personal operational systems, outside this work changelog, and do not need a project changelog. Use every remaining local `workspace:` as a possible source, whether or not it also has a `github:` URL; deduplicate records pointing to the same workspace or repository. Record entries with a `github:` URL but no local checkout as skipped rather than fetching them remotely.
2. **Determine the week window and target filename.** The target is `changelog/YYYY-MM-DD.md`, where `YYYY-MM-DD` is the **Monday on or before today** (if today is Monday, use today). The window is that Monday through the following Sunday inclusive, so a same-day entry counts. Reviewing on a Sunday closes the week that began on the previous Monday.
3. **Read each workspace's changelog.** For each local workspace from step 1, read source entries in the target window. The current convention is `changelog/YYYY-MM-DD-slug.md`; during transition also support a legacy root `changelog.md` or `CHANGELOG.md`. If a project's frontmatter sets `changelog_path`, use that exact path rather than assuming root — changelogs are sometimes nested (e.g. `docs/CHANGELOG.md`). If no known path and root has nothing, do one shallow search (`find <workspace> -maxdepth 3 -iname "*changelog*"`, excluding `node_modules`/`.git`) before concluding there's no changelog. Record the correct path back into the project's `changelog_path` frontmatter once found, so this doesn't get re-discovered every week. Skip and note a workspace with no readable changelog or no entries in the window; v1 never fetches remotely. The registry in `initiatives/changelog-for-me.md` records known paths and observed adoption.
3b. **Check local Beads as a fallback activity signal.** If a workspace has its own `.beads/` (i.e. runs local Beads independently of this planning repo), also check `bd -C <workspace> list --status=closed --all` for items closed in the window, even when step 3 found a changelog (some repos log via Beads, not prose, or do both unevenly). Summarize what a batch of closed issues actually did in a sentence or two — don't just list issue titles verbatim — and mark the bullet as sourced from Beads, not a changelog, so it's clear the repo still lacks a real changelog. This is how work gets missed silently: a repo can be genuinely active with no changelog file at all.
4. **Draft the roll-up.** Create `changelog/YYYY-MM-DD.md` with a `## This week across projects (<Mon D Mon> – <Sun D Mon>)` heading — spell out the explicit date range, not just the Monday filename date, since "week of X" reads ambiguously (leading up to X vs. starting from X) and this file is filename-dated by convention (Monday, per step 2) while the reader sees the heading, not the filename. Same applies wherever this content gets republished (e.g. on rufuspollock.com) — the range goes in the visible title, not just an implicit single date. Do not put this material in `week/`. **One bullet per project, not one per source entry.** This is a compaction, not a re-publication of the source changelog — if a project has one small entry this week, its bullet stays a plain clause; if it has several (like Reports That Matter's habit of many small entries some weeks, or a closed-Beads burst from step 3b), compact them into one top-level bullet — "Worked on Reports That Matter: ..." — summarized in a few sentences (a short paragraph is fine), not a run of separate bullets. Sub-bullets under that one project bullet are fine if it genuinely helps break up several distinct things, but the project gets exactly one entry in the list, followed by skipped eligible projects, all in the same list. Link the project name to `changelog_url` when set; otherwise use `url`, then `github`. When `changelog_path` and `github` are set, also include a concise source link to `{github}/blob/main/{changelog_path}` for the reader who wants the full detail. If an entry has an image, replace its repository-relative source with `https://raw.githubusercontent.com/<org>/<repo>/main/<image-path-as-written-in-the-entry>`, using the project's `github:` URL.
5. **Check for promotion flags.** An entry with `promote: true` in its frontmatter is a candidate. It still gets its normal main-list bullet and is also listed under `## Promotion candidates`, with one sub-heading and one caption option of 1–2 plain sentences. Use the entry's raw GitHub image URL when available. The human chooses whether and where to post; this skill never posts anything itself. Legacy sources without frontmatter have no promotion signal and are not inferred as candidates.
6. **Newsletter (only if asked).** If it's a newsletter week, the promoted items list from step 5 is the starting shortlist — human curates further, this skill doesn't draft newsletter copy unprompted.
7. **Publish to rufuspollock.com.** Once a week's draft exists here, publish it to `~/src/rufuspollock/rufuspollock.com`'s `/changelog` bucket (`changelog/YYYY-MM-DD.md`, Monday-dated, frontmatter `title: Week of <range>` + `created:`; update `changelog.md`'s base-query listing if it's a new file). Deploy is just `git commit` + `push` to `main` (Flowershow rebuilds automatically). This step runs on AI judgment, not a Rufus review gate — see Publishing judgment below. Don't wait to be asked for each week; if a draft exists and hasn't been published, publish it as part of running this skill.

## Publishing judgment (no review gate)

Rufus has said his default is to trust the judgment call here rather than review each week — apply it, don't route back for sign-off. Two things still get real scrutiny before anything goes out:

- **Beads-derived entries** (step 3b) weren't written for a public reader — they're internal issue titles. Rewrite them properly for a reader, don't just compact and ship verbatim.
- **A quick privacy/suitability check** on every entry before publish: no named third parties without clear prior consent to be named, no financial figures, no HR/legal/personal-life content, nothing that reads badly out of context. In practice this is rarely triggered because the source (project-repo changelogs) is already public-facing by construction — but check, don't assume, especially once sources like Life Itself Comms or coordination/team-process work start feeding this (people- and decision-heavy, unlike "fixed 166 broken links").

This judgment call applies to the rufuspollock.com publish step. It does not extend to promotion (step 5/6) — posting to social media or a newsletter is a different, more public action and stays human-chosen.

## Boundaries

- Steps 1–6 (the internal draft) are drafting only; step 7 (site publish) is the one place this skill takes a real action, and it does so on judgment per above — everything else stays a draft.
- Promotion/newsletter posting (steps 5–6) is never auto-posted — the human chooses whether and where.
- No remote-API fetching of a project's changelog — local checkouts only; say so when a project gets skipped for that reason rather than silently omitting it.
- Don't let this turn into a full portfolio review — it's strictly "what shipped and got logged this week," not project status in general (that's the `planning` skill's job).
